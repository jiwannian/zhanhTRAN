# PDF 翻译插件工程经验与排障索引

整理日期：2026-11-03；当前源码版本：1.0.23。本文总结本项目历次需求、失败和可核对的实现；不是对所有 PDF 的正确性保证。具体运行结果见 [验证记录](VALIDATION.md)。历史请求不等于已实现、模拟翻译不等于真实供应商质量评估。

## 1. 先明确当前契约，避免修复目标相互矛盾

早期方案以保留原字号为先，允许正文续页、表格增高续表、图内 OCR 扩框。它解决了部分容纳失败，却可能破坏图文关系。**自 1.0.18 起，PDF 的现行规则是固定原区域、放不下再统一缩字**；旧续页规则仅为历史，不可同时套用。

| 项目 | 当前规则 |
| --- | --- |
| 区域 | 保留位置、栏、首行/悬挂缩进及对齐，不借相邻空白、不挤图注 |
| 容纳 | 先原字号；失败后求区域内完整容纳的最大比例，不截断或改写 |
| 样式 | 区域内部统一比例，保留粗斜体和相对字号；缩进不随字缩放 |
| 页及表格 | 一源页一译页，不新增页，不改变列宽、行高、边框或图片位置 |
| 大幅缩字 | 用户明确不设人为比例下限；可读性是这一取舍的代价，不能把意外误识别造成的极小字号当成功 |
| 失败 | 坐标损坏、占位符丢失、字形不可用或数值失效时报告具体区域，不交付部分文件 |
| 范围 | PDF 新规则不应连带改变独立图片文件的既有输出路径 |

**可迁移原则：需求变更必须版本化，并同步替换实现、测试断言、错误提示和文档。** 不能只改成功路径，留下“长译文必须失败”或“必须新增续页”的旧断言。

## 2. PDF 内容流、视觉行和语义段落是三个层次

PDF 中的提取块常由绘制顺序、字体切换或定位操作形成，并不等于段落。逐块翻译会把一句话切碎；无条件合块又会吞掉下一条定义、列表或另一栏。

处理顺序：

1. 过滤纯空白、偏移定位片段；它们不应决定字号、缩进或行距。
2. 用主要可见文字的 **baseline** 判断行关系，而非 bbox 顶部；上标、混合字体会改变字框顶部。
3. 综合正文起点、行距、阅读顺序、物理间隔和结构边界恢复段落。
4. 同一段落的源视觉折行视为软换行，模型额外的换行或句号不应制造新的固定小框。
5. 真段落、下一编号、标题、分栏、目录、图注、脚注及表格边界必须保留。

“右侧还有空白”不表示可以跨越语义边界；反之，“源 PDF 换了一视觉行”也不表示必须拆成独立翻译单元。应先判定结构，再决定区域内连续排版。

## 3. 编号、缩写键和正文分离，但保留行归属

### 3.1 列表与目录

- 编号/项目符号保留源位置，正文使用自己的起点与悬挂缩进；不能将时间、年份、小数或普通数量误判为列表编号。
- 目录分别保存编号列、标题、引导点和页码列；只翻译标题，页码仍在源右对齐位置。
- 固定区域缩字不应将编号、页码或标记一起拖到正文新起点。

### 3.2 无边框定义表

1.0.21 的正文合并使相邻缩写释义并为一段；TTSN 字符仍在，但独立行归属消失。1.0.22 增加两列定义结构后，1.0.23 又暴露出全大写白名单、固定两倍字号间隔的不足。

改进方法：

- 使用重复的键列起点、释义列起点、相邻基线及真实 gutter 识别，不为某几个缩写硬编码。
- 允许空格、句点、混合大小写、小写/单字符单位、斜线及数字；候选间隔需由重复列位置支持，避免把键内空格当列间隙。
- 识别容差只用于判断同类结构，不能把源本来不同的释义起点强制移成一个坐标。
- 完整键复用源字形，只翻译释义；源释义续行归本条，下一键开始新条。
- 只消费被完整覆盖的原文本块；部分覆盖不能吞掉其他正文。
- 已识别正确的行可作邻行的几何锚点，但不能重复输出。

`B. S.` 被列表规则先拆成 `B.` 和 `S.`，以及 `MoCTCA`/`Mtrs` 错并一行，说明**解析器优先级和字段归属同样需要回归测试**。

## 4. 缓存修复必须保守，不能靠猜分句

保持 `schema: 1`，以可选结构元数据扩展；旧缓存缺少信息时可从对应源区域补取几何、基线和完整键。恢复旧合段译文须同时满足：

- 源键齐全且唯一，缓存中的顺序可确认，释义非空；
- 样式和受保护 token 能明确归属到各自区域；
- 剔除残留键必须由源完整键、旧前缀位置和原请求共同确认。

缺键、重复、乱序、空值、复杂样式歧义应明确失败并要求重新翻译，不能静默猜拆。导出阶段可恢复已确认的结构，不应因此请求新的模型译文。

## 5. 符号保护是数据完整性，不只是字体选择

- 保护完整坐标、数值和角度/分秒符号；兼容跨字体片段、空格分隔和特殊引号 `U+201F`。
- 列表标记分离后，正文仍须经过坐标保护，不能因“这是列表”提前跳过。
- 仅在正文实际发生替换后登记占位内容；独立标记不能再成为正文未引用的 token。
- 对私有字体符号或特殊编码优先复用源 PDF 字形/矢量，不能假设 Unicode 码点能由中文字体正确重建。
- 对新绘文字检查字形覆盖并回退；`.notdef` 白框不是成功。
- 完整性和样式闭合须逐区域检查，邻区存在同名 token 不能补成本区“完整”。

1.0.19 的教训是：**元数据中“登记了保护项”不等于正文中“替换了保护项”**。两者必须通过实际引用关系对账。

## 6. 固定区域缩字：先验证真实字形，再搜索比例

容纳判定应使用可见字形范围，避免字体空白上下边界造成不必要缩字。先试原字号；失败后逐次减半找到可容纳区间，再二分寻找最大可用比例，精度约原字号的 0.1%。

区域内各样式共用一个比例，保持相对字号；定位锚点与缩进独立于比例。每次候选都检查完整文本、字形范围及数值有效性。最终报告固定框、原字号、实际字号和比例。

这是固定译文、固定字体/排版策略下的容纳搜索，不是“任意翻译都可读”的保证。不能用更小的字掩盖错误段落合并、错误列归属或过紧的错误区域。

## 7. 性能优化：复用分析与有界并发

### 7.1 每页一次分析

`PageAnalysis` 复用页面文本、惰性 raw glyph、绘图、字体及表格信息，按区域取用，减少逐框重复扫描。解析时保留行坐标、样式、单元格信息供导出复用。

相同图片可按内容与尺寸缓存 OCR 结果，但结果必须复制后按每个图片实例的页面位置转换；不能复用旧实例的坐标。缓存需有界、按文档清理。改变识别分辨率或范围不是等价的性能优化。

### 7.2 翻译请求

- 默认并发 2，设置范围 1–10；按源 ID 回填，完成顺序不影响文档顺序。
- 保持模型、批次内容和上下文组织；性能优化不应偷换成省略翻译单元。
- 限流遵循 `Retry-After` 并降低并发；取消或不可恢复失败停止兄弟请求及排队任务。
- 完整性、公式/符号占位符与样式仍逐单元校验；只补未成功内容，共享有限重试预算，避免嵌套重试放大。

测试应覆盖乱序、1/10 并发上限、限流等待、缺条补译、取消和失败后无迟到进度，而非只测吞吐。

## 8. 进度是已完成工作的账本

阶段预算：解析 0–20%、翻译 20–80%、生成文件 80–98%、附件导入 98–100%。具体导出回调可在生成阶段预算内保守推进，不需要虚构估算速度。

分别显示页数、翻译完成项、排版页组、已导入附件。按唯一成功 ID/完成工作计数，重试不重复加分；全部文件生成并导入前至多 99%。失败和取消不能因 finally 清理而跳到 100%。

桥接协议：stdout 仅一个最终 JSON，stderr 传带独立标记的进度。依赖库提示、调试日志和警告都不能污染机器可读输出。应单独测试 CLI 原始 stdout/stderr，而非只测试 Python 函数返回值。

## 9. 可复用排障与验收流程

1. **锁定实物**：记录启用版本、包 SHA、源/译文区域 ID、阶段、错误码、几何与样式；截图是线索，不是完整根因证明。
2. **最小复现**：构造每份 1–3 页的合成材料，覆盖触发结构，不用用户论文或其他大论文验证。
3. **真旧版 A/B**：使用实际归档版本的解析器/导出器、相同 PDF 字节与相同译文缓存；不能把 Git HEAD 或模拟旧逻辑冒充发布基线。
4. **按条对应**：除全文完整，还检查每条源键与释义的行、列、基线、字号；“全文字符串仍存在”无法发现错并行。
5. **多层证据**：源码单元测试 → JS/Python 真实桥接 → 隔离宿主 → Poppler 最终渲染逐图目检；各层互不替代。
6. **不变量**：源文件哈希、原文侧像素、受保护键像素、缩进、完整文本、无缺字、无越界/覆盖、页数和导航。
7. **几何矩阵**：旋转 0/90/180/270、两种双语左右顺序、多源页、书签和内部链接；逐项说明由哪层测试覆盖。
8. **发布闭环**：审查公共文件清单，排除密钥、论文和日常配置；源码与基于实际归档基线的补丁应能重建同字节 XPI。
9. **安装独立验收**：构建成功不等于已安装，安装不等于当前已启用。隔离 profile 验收不能冒充日常安装完成。

先更新版本元数据再启动相关测试，避免测试启动时读入旧 expected 值造成竞态。只运行本轮修改与关联测试；失败日志保留，但最终结论必须绑定最终包字节。

首次公开同步的 GitHub Linux CI（[运行记录](https://github.com/jiwannian/zhanhTRAN/actions/runs/41640820725)）暴露出与 Windows 既有验收不同的测试环境假设：

- JavaScript 110 项中 109 项通过，独立启动测试仍将版本写死为 1.0.1；本轮已将其改为核对 manifest 与 package 版本一致，并在本地复现旧断言失败、确认修正后 1 项通过。
- Python 自动发现 336 项，报告 5 个失败、61 个错误。错误中 57 个来自字体资源无法打开，4 个来自把 stderr 每一行都当作进度 JSON；失败涉及 stderr 必须为空的假设，以及 Linux 字体回退没有独立粗体时的样式断言。
- 部分 OCR 合成夹具直接使用 Windows 的 Arial/Times 路径；当前 CI 只安装文泉驿，而该回退将同一个字体文件用于普通和粗体。fontTools 在此环境还会输出字体表诊断。以上是已回读日志的环境/测试线索，不表示所有失败都已修复。

因此，**当前仓库 Linux CI 尚未全绿**。本轮只修正与发布版本关联的陈旧断言；未为消除 CI 红灯而删测、跳过失败或改动已交付 XPI，也没有将历史 Windows 隔离验收冒充 Linux 成功。跨平台字体夹具、真实粗体及 stderr 诊断兼容仍需单独处理；本轮没有新建 GitHub Release。

可迁移教训：测试依赖也要列入环境契约；stdout 单 JSON 与 stderr 可携带带标记进度/诊断是不同约束。公开同步成功、打包成功、平台测试通过和实际安装，必须分别报告。
